# 하네스 설계

> 하네스가 무엇으로 구성되고 어떤 순서로 작동하는지를 담은 정본.
> 구조를 바꿀 때는 이 문서를 먼저 고치고 구현을 따라오게 한다.
> 진행 이력은 [progress.md](progress.md), 프로젝트 맥락은 [../CLAUDE.md](../CLAUDE.md).

**Last Updated**: 2026-09-08

---

## 무엇인가

새 프로젝트에 `.claude/` 폴더를 떨궈 넣으면 기획부터 릴리스까지 정해진 순서로 움직이게 만드는 작업 틀이다.

두 종류의 프로젝트를 모두 받는다. 아이디어만 있는 개인 프로젝트와, 기획이 이미 끝나 있는 회사 제품이다. 시작점만 갈라지고 그 이후 개발 과정은 같다.

## 전제

혼자 개발하는 사람이 쓴다. 남의 코드를 리뷰하거나 팀 컨벤션을 맞추는 절차는 다루지 않는다.

배포와 운영 감시는 회사 인프라에 종속되므로 하네스가 대신하지 않는다. `/ship`은 PR 생성까지 하고 그 뒤는 각 조직의 파이프라인에 맡긴다.

## 작업 프로세스

### 프로젝트를 열 때 — 한 번

```
/kickoff
  │
  │  Q. 새로 시작하는 아이디어인가, 기획이 이미 있는가
  │
  ├─ 새로 시작 ──→ 아이디어 검증 → 제품 정의 → 범위 조정
  │
  └─ 기획 있음 ──→ 기존 기획 문서를 읽어 요약과 확인
  │
  ▼  두 경로가 여기서 합류
  │
  system-architecture 스킬
    Step 1  요구 수집      묻기만 한다. 아무것도 고르지 않는다
    Step 2  데이터 모델    엔티티와 관계. 저장 기술은 아직 안 정한다
    Step 3  기술 선택      1과 2를 근거로 언어·프레임워크·DB·초기 배포
    Step 4  시스템 구조    덩어리 나누기, 통신 방식, 횡단 관심사
  │
  ▼
  @plan-reviewer 검토 → 사용자 승인 → docs/ 확정
  │
  ▼
  CI 설정이 있는지 확인. 없으면 만들지 물어본다
```

Step 2를 Step 3보다 앞에 두는 이유는 데이터의 모양이 드러나야 저장소 선택이 근거를 갖기 때문이다. 순서를 바꾸면 데이터 성격을 모른 채 DB를 고르게 된다.

각 Step 끝에서 확인하고 넘어간다. 뒤 Step에서 앞이 틀렸다고 드러나면 앞으로 돌아간다.

### 기능 하나를 만들 때 — 반복

```
/feature-start <이름>
  │  Q. 범위가 어디까지인가 — 백엔드 / 프론트 / 양쪽
  │  Q. 문서가 필요한 크기인가
  │
  ├─ 작음 ──→ tasks.md 한 줄로 끝. 아래를 건너뛴다
  │
  └─ 큼 ───→ prd.md             왜 만드는가
             functional-spec.md  무엇이 어떻게 동작하는가
             screens.md          화면이 있을 때만
  │
  ▼
/feature-plan <이름>
  │  tech-spec.md 작성
  │  아키텍처에 영향이 있으면 architecture.md 갱신 + ADR
  │  tasks.md 에 단계 분해
  │  feature/<이름> 브랜치 생성
  │
  ▼
/task            할 일 하나 진입. 관련 문서 자동 로드
  │
  │  ... 대화하며 구현 ...
  │
/done            AC 검증 → 체크오프 → 커밋
  │
  └─ 다음 할 일로 반복
  │
  ▼
/code-review     변경 리뷰
/qa              백엔드면 API 시나리오, 화면이 있으면 브라우저
/design-review   화면이 있을 때
  │
  ▼
/ship            CI 결과 확인 → 스키마 변경 검사 → 버전 → CHANGELOG → PR
```

### 수시로

| 커맨드 | 언제 |
|---|---|
| `/decision` | 결정이 생긴 그 자리에서 ADR 로 기록 |
| `/investigate` | 버그 원인을 모를 때 |
| `/perf` | 부하와 응답 시간 측정, 이전 기준선과 비교 |
| `/update-docs` | 세션 끝에 문서 일괄 갱신 |
| `/project-status` | 오랜만에 돌아와 현재 위치 파악 |
| `/compile-spec` | 마일스톤 끝에 전체 명세와 README 갱신 |
| `/cleanup` | 기술 부채 점검 |
| `/security-audit` | 주기적 보안 감사 |

### 단계가 올라갈 때

마일스톤이 끝나면 `system-architecture` 를 다시 돌린다. 이때 스킬은 묻기만 하지 않고 **무엇이 달라져야 하는지 후보를 먼저 내놓는다.** 사용자가 무엇을 바꿔야 하는지 모르는 상태라고 전제한다.

**PoC 에서 MVP 로** — 임시 저장소를 실제 DB 로 교체, 인증과 권한 붙이기, 개발과 운영 환경 분리, 에러 처리 정비, 로그와 응답 시간 기록, 백업 방식, 스키마 변경 절차.

**MVP 에서 제품화로** — 실제 부하 측정, 잰 결과를 근거로 필요한 곳에만 캐시나 읽기 분리, 모니터링과 알림, 배포 자동화, 장애 대응 절차, 보안 전면 감사.

검토 결과는 `architecture.md` 를 현재 상태로 덮어쓰고, 왜 바뀌었는지는 ADR 로 남긴다. 전환 기록을 위한 별도 문서는 만들지 않는다. ADR 에 `[milestone: <이름>]` 태그를 달면 그 전환에 걸린 결정만 모아 볼 수 있다.

## 문서 세트

```
프로젝트 루트/
├── README.md                 제품 개요와 실행 방법 — 생성물
├── CLAUDE.md                 프로젝트 규칙
└── docs/
    ├── plan.md               제품 방향
    ├── milestones.md         마일스톤
    ├── architecture.md       시스템 구조 — 현재 상태만
    ├── data-model.md         데이터 모델
    ├── context.md            결정 기록 (ADR) 과 구현 스냅샷
    ├── tasks.md              진행 인덱스
    ├── spec-index.md         전체 기능 명세 — 생성물
    ├── screens-index.md      전체 화면 목록 — 생성물
    └── features/<이름>/
        ├── prd.md            왜 만드는가
        ├── functional-spec.md 무엇이 어떻게 동작하는가
        ├── screens.md        어떻게 보이고 조작되는가
        └── tech-spec.md      어떤 코드로 만드는가
```

### 문서마다 답하는 질문

| 문서 | 답하는 질문 | 담지 않는 것 |
|---|---|---|
| `plan.md` | 왜 만들고 무엇을 만들고 어디로 가는가 | 진행 상태, 기한, 측정 수치, task 코드 |
| `milestones.md` | 언제까지 무엇을 내고 무엇이 되면 끝인가 | 할 일 하나하나 |
| `architecture.md` | 시스템이 지금 어떤 모양인가 | 과거 구조, 왜 그렇게 됐는지 |
| `data-model.md` | 어떤 데이터를 어떤 관계로 어디에 두는가 | 구현 코드 |
| `context.md` | 왜 그렇게 결정했는가, 지금 어디까지 구현됐는가 | 시도 단계별 스토리, 측정 raw |
| `tasks.md` | 지금 무엇을 하고 다음에 무엇을 하는가 | 코드 수준 AC, 함수명 |
| `prd.md` | 이 기능을 왜 만드는가 | 동작 규칙, 화면 구성 |
| `functional-spec.md` | 무엇이 어떻게 동작하는가 | 구현 방식, 화면 배치 |
| `screens.md` | 화면에 무엇이 놓이고 어떻게 움직이는가 | 비즈니스 규칙 |
| `tech-spec.md` | 어떤 API·테이블·코드 구조로 만드는가 | 왜 이 기능이 필요한가 |

`plan.md` 는 6개월 뒤에도 그대로일 내용만 담는다. `architecture.md` 는 항상 현재 상태만 담고 이력을 남기지 않는다. 왜 바뀌었는지는 전부 `context.md` 의 ADR 이 갖는다.

### 기능 폴더는 범위와 크기에 따라 달라진다

| 범위 | 만드는 문서 | 검증 |
|---|---|---|
| 백엔드만 | prd, functional-spec, tech-spec | API 시나리오 |
| 프론트만 | prd, functional-spec, screens, tech-spec | `/qa` + `/design-review` |
| 양쪽 | 위 전부 (API 계약을 먼저 확정) | API 시나리오 + `/qa` |

작은 기능은 폴더를 만들지 않고 `tasks.md` 항목 하나로 끝낸다. `/feature-start` 가 시작할 때 크기를 판단한다.

### ADR 태그

`[product]` `[feature: <이름>]` `[tech]` `[architecture]` `[infra]` `[security]` `[data]` `[milestone: <이름>]`

여러 개를 같이 붙일 수 있다. 마일스톤 태그는 단계 전환에 걸린 결정을 모아 보기 위한 것이다.

## 설계 원칙

**되돌리기 어려운 것만 먼저 정한다.** 데이터 저장 방식, 서비스 분리, 동기와 비동기, 인증 방식은 처음에 정한다. 서버 대수, 캐시, 읽기 복제본, 인덱스는 필요해진 다음에 붙인다.

**확장 지점을 열어두되 확장을 구현하지 않는다.** DB 접근을 한 계층에 모으고, 외부 호출을 인터페이스 뒤에 두고, 무거워질 처리를 함수로 떼어 둔다. 미리 만드는 비용은 거의 없고 안 해두면 나중 비용이 크다.

**재기 전에 최적화하지 않는다.** 대신 재는 장치를 먼저 넣는다. 응답 시간과 쿼리 횟수를 남겨두면 어디가 느린지 추측하지 않아도 된다.

**개별 문서가 정본이고 취합본은 생성물이다.** 기능별로 쓰고 `/compile-spec` 이 모은다. 반대로 하면 여러 기능을 동시에 진행할 때 충돌한다.

**최신 상태만 남긴다.** 문서를 고칠 때 대조나 이력 문구를 본문에 남기지 않고 처음부터 그렇게 쓴 것처럼 다시 쓴다. 이력은 ADR 과 git 이 갖는다.

**공통 규칙은 한 곳에 둔다.** 말투, 승인 절차, 에이전트 호출 방식 같은 규칙을 커맨드마다 복사하지 않는다. `CLAUDE.md` 템플릿에 두고 커맨드에는 그 커맨드만의 규칙을 남긴다.

**사용자가 모른다고 전제하고 먼저 묻는다.** 나중에 바꾸면 비싼 결정은 사용자가 말해주기를 기다리지 않고 시스템이 먼저 물어본다. 단계 전환에서도 무엇이 달라져야 하는지 후보를 먼저 내놓는다.
