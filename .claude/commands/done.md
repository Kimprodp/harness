# /done — 작업 완료 처리

당신(메인 AI)은 방금 끝낸 작업을 마무리한다. 완료 조건을 검증하고, `docs/tasks.md` 를 체크오프하고, 커밋한다.

`/task` 가 작업의 시작이라면 이 커맨드는 끝이다.

---

## 이 커맨드만의 규칙

> 말투, 승인 절차, 커밋과 푸시 규칙 같은 공통 규칙은 `CLAUDE.md` 의 공통 작업 규칙을 따른다.

1. **AC 검증 없이 체크오프하지 않는다.** 확인할 수 없는 항목은 사용자에게 묻는다.
2. **커밋 메시지를 요청 없이 먼저 제안한다.** 사용자가 "커밋해줘" 라고 말할 때까지 기다리지 않는다.
3. **푸시하지 않는다.** 사용자가 명시적으로 요청할 때만 한다.
4. **기능 전체가 끝났을 때만 아카이브를 제안한다.** 항목 하나 완료로는 옮기지 않는다.

---

## Phase 0: 대상 확인

`docs/tasks.md` 에서 `⏳` 표시된 항목을 찾는다. 없으면 최근 변경과 대화 맥락으로 추정해 사용자에게 확인한다.

```bash
git status --short
git diff --stat
```

변경이 없으면 알리고 종료한다.

---

## Phase 1: AC 검증

작업 항목의 완료 조건을 하나씩 확인한다. 코드 수준 조건은 `docs/features/<X>/tech-spec.md` 에, 동작 규칙은 `functional-spec.md` 에 있다.

### 1-1. 코드로 확인 가능한 것

`git diff` 로 변경 내용을 확인한다. 조건에 해당하는 코드가 실제로 들어갔는지 본다.

### 1-2. 테스트

테스트가 있으면 실행한다. 프로젝트 러너를 감지해 관련 테스트만 돌린다.

| 감지 | 명령 |
|---|---|
| `package.json` 의 test 스크립트 | `npm test` |
| `pom.xml` | `mvn test` |
| `build.gradle` | `gradle test` |
| `pyproject.toml` | `pytest` |
| `Cargo.toml` | `cargo test` |
| `pubspec.yaml` | `flutter test` |

실패하면 이번 변경 때문인지 원래 깨져 있던 것인지 구분해 보고한다. 이번 변경 때문이면 체크오프하지 않는다.

### 1-3. 수동 확인이 필요한 것

화면 표시처럼 코드로 확인할 수 없는 조건은 사용자에게 묻는다.

```
완료 조건 확인:
  ✅ <자동 확인된 항목>
  ✅ <테스트 통과 항목>
  ❓ <수동 확인 필요 항목> — 확인하셨나요?
```

### 1-4. 미충족 상태로 완료 처리

사용자가 일부 미충족을 알고도 완료로 처리하겠다고 하면 진행하되, 체크오프 옆에 메모를 남긴다.

```markdown
- [x] **<제목>** [M] ✅ 2026-09-08 (AC 2 미충족 — 후속 작업 필요)
```

그리고 후속 작업을 `tasks.md` 에 추가할지 묻는다.

---

## Phase 2: 체크오프

### 2-1. tasks.md 갱신

1. `[ ]` → `[x]`
2. `⏳` 표시 제거
3. 완료일 추가: `[x] **<제목>** [M] ✅ 2026-09-08`
4. **원래 위치에 그대로 둔다.** 옮기지 않는다. 맥락이 사라진다

### 2-2. 문서와 코드가 어긋났으면

구현 중에 설계와 다르게 만든 부분이 있으면 여기서 문서를 고친다. 미루면 다음 세션이 틀린 문서를 읽는다.

- 동작 규칙이 바뀌었으면 `functional-spec.md`
- 설계가 바뀌었으면 `tech-spec.md`
- 화면 구성이 바뀌었으면 `screens.md`

큰 변경이면 `/decision` 으로 ADR 을 남긴다.

---

## Phase 3: 커밋

### 3-1. 메시지 작성

**제목**은 `tasks.md` 의 작업 이름을 그대로 활용한다. 타입 접두사(`feat:`, `fix:`, `refactor:`, `docs:`, `test:`)를 작업 성격에 맞게 붙인다.

```
tasks.md:  - [x] 2. SQL 가설 검증 라운드 수 늘리기
→ 제목:    feat: SQL 가설 검증 라운드 수 늘리기
```

**본문**은 하위 작업이 있으면 자연어로 한두 줄씩, 없으면 무엇을 했는지 한 문장으로 쓴다.

| 쓰지 않는 것 | 쓰는 것 |
|---|---|
| "files modified: 3, lines: +42 -18" | "라운드 횟수 파라미터 추가하고 결과 일관성 체크" |
| "src/foo.py, src/bar.py 수정" | (파일명 나열하지 않는다) |
| "관련 파일들 변경 사항 적용" | "DB 스키마에 round_count 컬럼 추가" |
| "코드 X건, 테스트 Y건 수정" | "검증 로직 정비와 테스트 추가" |

원칙은 하나다. **동료가 한 눈에 무엇을 했는지 알 수 있어야 한다.** 변경 통계나 파일 목록은 git 이 이미 갖고 있다.

이슈 트래커를 쓰는 프로젝트면 `tasks.md` 항목에 적힌 이슈 번호를 본문 끝에 넣는다.

### 3-2. 제안과 실행

```
📝 커밋 메시지 제안:

  <메시지 초안>

  대상: <변경 파일 수>개 파일

진행할까요? (Y / N / 수정)
```

승인하면 커밋한다. 커밋 해시를 기억해 둔다. 기능 아카이브 때 단계별로 매핑한다.

거절하면 건너뛴다. 다음 작업과 묶어 커밋하겠다는 뜻이다.

**푸시하지 않는다.**

---

## Phase 4: 기능 완료 감지

체크오프 후 이 작업이 속한 `### 기능: <X>` 섹션의 모든 항목이 `[x]` 인지 확인한다. 하나라도 미완료면 Phase 5 로 간다.

### 4-1. 민감 영역 판정

기능명이나 `prd.md` 본문에 `.claude/settings.json` 의 `reminders.security_sensitive_keywords` 가 포함되면 `.claude/state/security-audit.json` 의 `sensitive_changes_since_last_audit` 에 기록한다.

```json
{ "date": "2026-09-08", "feature": "<X>" }
```

그리고 감사를 권한다.

```
🔒 기능 "<X>" 은 민감 영역입니다.

아카이브 전에 보안 감사를 권합니다: /security-audit <X>

지금 실행할까요? (Y / N)
```

Y 면 `.claude/commands/security-audit.md` 를 Read 로 로드해 해당 범위로 실행하고 돌아온다.

### 4-2. 아카이브 제안

```
🎉 기능 "<X>" 완료. 하위 작업 <N>개가 모두 끝났습니다.

"완료된 기능" 섹션으로 옮길까요? (Y / 나중에)
```

승인하면 **압축해서** 옮긴다. 원본 항목을 그대로 옮기지 않는다.

```markdown
### 기능: <X> (완료: 2026-09-08)

> PRD: [`features/<X>/prd.md`](features/<X>/prd.md)
> ADR: [`context.md`](context.md) `[feature: <X>]`

<한 줄 요약 — 무엇을 만들었고 결과가 무엇인지. 성과와 미달 모두>

#### 단계
1. <단계명> — <짧은 설명> (`커밋해시`)
2. <단계명> — <짧은 설명> (`해시1`, `해시2`)

#### 코멘트
- <중요한 변경이나 보류 사항. 상세는 ADR>
- 미진행 후속: <항목> — <어디로 넘겼는지>
```

**압축 원칙**

- 원본 항목의 AC 를 그대로 옮기지 않는다
- 측정 raw 나 토큰 수 같은 디테일은 ADR 이나 측정 로그로
- `T1`, `T2` 같은 접두사를 쓰지 않는다. 숫자나 자연어 단계명만
- 한 줄 요약에 성과와 미달을 모두 적는다

커밋 해시는 Phase 3 에서 누적된 것과 `git log <시작시점>..HEAD --oneline` 으로 보강해 단계별로 매핑한다. 애매하면 사용자에게 짧게 확인한다.

### 4-3. 마일스톤 갱신

`docs/milestones.md` 의 해당 마일스톤 포함 기능 표에서 이 기능의 상태를 완료로 바꾼다.

마일스톤의 모든 기능이 완료됐으면 알린다.

```
🏁 마일스톤 "<이름>" 의 기능이 모두 완료됐습니다.

- 완료 판정 기준 확인: <기준 원문>
- /compile-spec 으로 전체 명세와 README 를 갱신할 수 있습니다
- 다음 단계로 넘어간다면 /architecture 로 구조를 점검하세요
```

---

## Phase 5: 후속 제안

이번 작업의 성격을 보고 하나만 제안한다. 매번 여러 개를 나열하지 않는다.

| 이번 작업에 있었던 것 | 제안 |
|---|---|
| 라이브러리·외부 서비스 채택, 아키텍처 패턴 결정 | `/decision` — 맥락이 뜨거울 때 ADR 로 |
| 세 개 이상 파일에 걸친 큰 변경, 문서 여러 곳 영향 | `/update-docs` |
| 기능 전체 완료 | `/code-review` |
| 화면 변경 | `/design-review` |
| 그 외 | 제안 없음 |

```
✅ 완료: <작업 제목>

<위 표에 해당하는 제안이 있으면 한 줄>

다음:
- 이어서 작업: /task
- 종료: "나중에"
```

사용자가 이어서 작업을 원하면 `.claude/commands/task.md` 를 Read 로 로드해 다음 항목으로 진입한다.

---

## 실패 시나리오

| 상황 | 대응 |
|---|---|
| 진행 중 항목이 없음 | 최근 변경과 대화 맥락으로 추정 후 확인 |
| 변경 사항 없음 | 알리고 종료 |
| 테스트 실패 | 이번 변경 탓인지 구분해 보고. 이번 탓이면 체크오프하지 않음 |
| AC 일부 미충족 | 사용자 판단에 따라 메모와 함께 완료 처리, 후속 작업 추가 제안 |
| 커밋 거절 | 건너뛴다. 다음 작업과 묶는 것으로 간주 |
| 기능 완료인데 커밋 해시 매핑이 애매 | 사용자에게 짧게 확인 |
| 구현이 설계와 어긋남 | Phase 2-2 에서 문서를 먼저 고친 뒤 커밋 |
