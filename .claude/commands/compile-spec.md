# /compile-spec — 명세 취합

당신(메인 AI)은 `docs/features/` 아래의 기능 문서를 전부 읽어 전체를 조망하는 문서를 만든다.

**왜 필요한가**: 개발은 기능 단위로 진행되므로 문서도 기능 폴더에 쓴다. 그런데 "지금 이 시스템 전체가 무엇을 하는가" 를 보려면 흩어진 것을 모아야 한다. 개발자와 QA 가 실제로 필요로 하는 시야다.

**개별 문서가 정본이고 여기서 만드는 것은 파생물이다.** 생성된 문서를 손으로 고치지 않는다. 고쳐야 하면 원본 기능 문서를 고치고 다시 생성한다.

**언제 쓰나**: 마일스톤을 마칠 때, `/ship` 직후, 오랜만에 전체를 봐야 할 때.

---

## 이 커맨드만의 규칙

> 말투, 승인 절차 같은 공통 규칙은 `CLAUDE.md` 의 공통 작업 규칙을 따른다.

1. **생성물에 원본에 없는 내용을 넣지 않는다.** 요약과 재배열만 한다. 빠진 것은 빠졌다고 표시한다.
2. **생성 파일 상단에 자동 생성물임을 명시한다.** 손으로 고치면 다음 실행에서 사라진다.
3. **덮어쓰기 전에 보여준다.** 무엇이 달라지는지 확인받고 쓴다.

---

## Phase 0: 선행 체크

1. `docs/features/` 존재 확인. 없거나 비어 있으면 안내 후 종료.
2. `docs/plan.md`, `docs/milestones.md`, `docs/tasks.md` 존재 확인. 없는 것은 리포트에 표시한다.
3. 인자 확인. `--only spec`, `--only screens`, `--only readme` 로 하나만 생성할 수 있다.

---

## Phase 1: 수집

`docs/features/*/` 를 Glob 으로 훑고 각 폴더에서 읽는다.

| 파일 | 뽑을 것 |
|---|---|
| `prd.md` | 한 줄 요약, 대상 사용자, 성공 지표 |
| `functional-spec.md` | 기능 목록, 각 기능의 동작 규칙 요약, 예외 처리 |
| `screens.md` | 화면 목록, 경로, 진입 경로, 화면 이동 |
| `tech-spec.md` | 엔드포인트 목록 (있으면) |

함께 읽는다.

- `docs/tasks.md` — 각 기능의 완료 여부
- `docs/milestones.md` — 어느 마일스톤에 속하는지
- `docs/plan.md` — 제품 한 줄 정의, 현재 단계
- `docs/architecture.md` — 실행 방법에 필요한 배포·기술 정보

기능 폴더가 없는 작은 작업은 `docs/tasks.md` 항목에서 완료된 것을 훑어 "기타 변경" 으로 모은다.

```markdown
## <기능명>

<prd 의 한 줄 요약>

**동작 규칙**

| 기능 | 입력 | 처리 | 출력 |
|---|---|---|---|

**예외 처리**

| 상황 | 처리 |
|---|---|

**엔드포인트** (있으면)

<!-- 기능마다 반복 -->

## 기타 변경

기능 폴더 없이 처리한 작업.

| 작업 | 완료일 |
|---|---|
```

**요약하되 규칙을 빠뜨리지 않는다.** 원본의 처리 규칙을 한 줄로 줄이더라도 조건과 분기가 사라지면 안 된다. 줄이기 어려우면 원본 링크만 두고 "상세는 원본" 이라고 적는다.

## Phase 3: `docs/screens-index.md` 생성

화면이 있는 기능이 하나도 없으면 이 문서를 만들지 않는다.

```markdown
# 전체 화면 목록

> 이 문서는 `/compile-spec` 이 생성합니다. 직접 고치지 마세요.
> 고칠 내용은 `features/<기능명>/screens.md` 에 반영한 뒤 다시 생성합니다.
>
> 생성: <YYYY-MM-DD>

## 화면 일람

| 화면 | 경로 | 소속 기능 | 권한 | 상태 |
|---|---|---|---|---|

## 화면 이동 구조

<!-- 기능별 이동도를 합쳐 전체 흐름으로. 겹치는 화면은 하나로 -->

```
[로그인] --> [대시보드] --> [목록] --> [상세]
                  │
                  └--> [설정]
```

## 기능별 화면

### <기능명>

| 화면 | 경로 | 주요 요소 |
|---|---|---|
```

**화면 이동 구조를 합칠 때 주의한다.** 여러 기능이 같은 화면을 가리키면 하나로 합치고, 이름이 다르면 그 사실을 표시한다. 같은 화면을 기능마다 다르게 부르고 있으면 그것 자체가 정리할 문제다.

## Phase 4: `README.md` 생성

프로젝트 루트의 `README.md` 를 만든다. 이미 있으면 갱신한다.

```markdown
# <제품명>

<plan.md 의 한 줄 정의>

**현재 단계**: <PoC / MVP / 제품화>

## 지금 되는 것

<완료된 기능 목록. 사용자 입장의 표현으로>

- <기능>: <무엇을 할 수 있는지>

## 아직 안 되는 것

<진행 중이거나 예정인 기능. 마일스톤 기준>

- <기능>: <어느 마일스톤>

## 실행 방법

### 요구 사항

<architecture.md 의 기술 스택에서>

### 설치

### 실행

### 테스트

## 문서

| 문서 | 내용 |
|---|---|
| [docs/plan.md](docs/plan.md) | 제품 방향 |
| [docs/architecture.md](docs/architecture.md) | 시스템 구조 |
| [docs/spec-index.md](docs/spec-index.md) | 전체 기능 명세 |
| [docs/screens-index.md](docs/screens-index.md) | 전체 화면 목록 |
| [docs/milestones.md](docs/milestones.md) | 마일스톤 |
```

**실행 방법을 지어내지 않는다.** `package.json` 의 스크립트, `Makefile`, `docker-compose.yml`, CI 워크플로에서 실제 명령을 읽어 쓴다. 찾을 수 없으면 `<TBD: 실행 명령 확인 필요>` 로 표시하고 사용자에게 묻는다.

기존 `README.md` 에 손으로 쓴 내용이 있으면 지우지 않는다. 어떤 절이 사람이 쓴 것인지 애매하면 사용자에게 확인한다.

## Phase 5: 확인과 반영

생성 전에 무엇이 달라지는지 보여준다.

```
📄 생성할 문서

  docs/spec-index.md     기능 7개 (신규 2, 변경 3, 유지 2)
  docs/screens-index.md  화면 12개 (신규 4)
  README.md              "지금 되는 것" 에 기능 2개 추가

⚠️ 원본에서 찾지 못한 것
  - features/payment/functional-spec.md 에 예외 처리 표가 비어 있음
  - features/report/screens.md 의 화면 3개에 권한 표기 없음

이대로 생성할까요?
```

**빠진 것을 조용히 넘기지 않는다.** 원본이 비어 있으면 생성물도 비게 되고, 그러면 취합 문서를 믿을 수 없게 된다. 무엇이 비었는지 알려서 원본을 채우게 한다.

승인 후 파일을 쓴다.

```
✅ 취합 완료

- docs/spec-index.md
- docs/screens-index.md
- README.md

원본이 비어 있던 곳: <목록>
채우려면 해당 기능 문서를 고친 뒤 다시 실행하세요.
```

## 실패 시나리오

| 상황 | 대응 |
|---|---|
| `docs/features/` 없음 | `/feature-start` 안내 후 종료 |
| 기능 폴더는 있는데 문서가 비어 있음 | 빈 곳을 목록으로 보고. 생성은 진행하되 해당 항목에 "원본 없음" 표시 |
| 화면이 있는 기능이 없음 | `screens-index.md` 를 만들지 않는다 |
| 같은 화면을 기능마다 다르게 부름 | 합치면서 그 사실을 표시. 이름 통일은 사용자 판단 |
| 실행 명령을 찾을 수 없음 | `<TBD>` 로 두고 사용자에게 질문 |
| 기존 README 에 손으로 쓴 내용 | 지우지 않는다. 애매하면 확인 |
| 기능이 너무 많아 문서가 큼 | 기능 일람 표는 전부 두고 상세는 링크로. 분할은 사용자와 상의 |
