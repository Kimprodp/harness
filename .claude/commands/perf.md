# /perf — 성능 측정

당신(메인 AI)은 엔드포인트에 부하를 걸어 응답 시간과 처리량을 잰다. 결과를 기준선으로 저장하고 다음 측정과 비교한다.

**왜 필요한가**: 추측으로 최적화하면 거의 항상 엉뚱한 곳을 고친다. 캐시나 읽기 분리 같은 것을 붙일지 판단하려면 먼저 재야 한다. `system-architecture` 스킬이 "재기 전에 최적화하지 않는다. 대신 재는 장치를 먼저 넣는다" 고 정한 것의 실행 도구다.

**`/qa` 와의 차이**: `/qa` 는 요청을 한 번씩 보내 동작을 확인한다. `/perf` 는 동시에 여러 번 보내 얼마나 견디는지 본다.

---

## 이 커맨드만의 규칙

> 말투, 승인 절차 같은 공통 규칙은 `CLAUDE.md` 의 공통 작업 규칙을 따른다.

1. **운영 환경을 대상으로 돌리지 않는다.** 실제 부하를 주는 도구다. 대상 주소를 확인하고, 운영으로 보이면 중단하고 확인받는다.
2. **코드를 수정하지 않는다.** 측정만 한다. 개선은 별도 작업이다.
3. **첫 측정에서 결론을 내지 않는다.** 기준선이 없으면 비교 대상이 없다. 숫자만 보고 느리다 빠르다 판정하지 않는다.
4. **쓰기 요청을 부하 대상에 넣을 때 데이터가 쌓인다는 점을 알린다.** 정리 방법을 함께 정한다.

---

## Phase 0: 선행 체크

1. `.claude/scripts/perf/bench.js` 존재 확인.
2. 대상 주소 확인. **`localhost` 나 사내 개발 주소가 아니면 멈추고 확인받는다.**

```
⚠️ 대상이 로컬이 아닙니다: <주소>

부하 측정은 대상 서버에 실제 트래픽을 보냅니다.
운영 환경이면 중단하세요.

  - "개발 서버가 맞다" → 진행
  - "중단"            → 종료
```

3. 서버가 응답하는지 확인. 안 되면 켜달라고 안내하고 중단.
4. 기준선 존재 확인: `.claude/state/perf-baseline.json`

## Phase 1: 대상 선정

### 1-1. 무엇을 잴 것인가

사용자 인자와 대화로 정한다. 정할 것은 이렇다.

- 어떤 엔드포인트인가
- 인증이 필요한가 (토큰을 어떻게 얻는가)
- 얼마나 오래, 몇 개를 동시에 보낼 것인가
- 목표가 있는가 (p95 몇 ms 이내 등)

`docs/architecture.md` 의 품질 목표 절을 먼저 읽는다. 정해진 목표가 있으면 그것을 임계값으로 쓴다.

### 1-2. 대상 고르는 기준

전부 재지 않는다. 다음에 해당하는 것부터 고른다.

- 사용자가 가장 자주 부르는 경로
- 목록 조회처럼 데이터가 늘수록 느려질 수 있는 것
- 외부 시스템을 호출하는 것
- 느리다는 인상이 있는 것

### 1-3. 설정값 제안

| 항목 | 기본 | 언제 올리나 |
|---|---|---|
| duration | 10초 | 변동이 커서 안정된 값이 필요할 때 |
| concurrency | 10 | 실제 예상 동시 사용자가 더 많을 때 |
| warmupMs | 1000 | 첫 요청이 유독 느린 환경 |

`docs/architecture.md` 의 규모 항목에 예상 동시 사용자가 적혀 있으면 그 값을 참고해 제안한다.

## Phase 2: 시나리오 작성과 승인

`.claude/scripts/perf/scenarios/<이름>.json` 에 저장한다.

```json
{
  "name": "list-api",
  "baseUrl": "http://localhost:8080",
  "headers": { "Authorization": "Bearer <토큰>" },
  "duration": 10,
  "concurrency": 10,
  "warmupMs": 1000,
  "targets": [
    { "name": "목록 조회", "method": "GET", "path": "/api/items?page=1" },
    { "name": "상세 조회", "method": "GET", "path": "/api/items/1" }
  ],
  "thresholds": { "p95Ms": 500, "errorRate": 0.01 }
}
```

승인을 받는다.

```
아래 설정으로 측정합니다.

  대상: http://localhost:8080
  기간: 10초 × 2개 엔드포인트 (준비 운동 1초 별도)
  동시: 10
  임계: p95 500ms, 오류율 1%

  1. GET /api/items?page=1
  2. GET /api/items/1

총 약 25초 걸립니다. 진행할까요?
```

쓰기 요청이 포함되면 알린다.

```
⚠️ POST 요청이 포함돼 있습니다. 측정 중 데이터가 계속 쌓입니다.
   측정 후 정리 방법을 정해두시거나, 조회만으로 재는 것을 권합니다.
```

## Phase 3: 실행

```bash
node .claude/scripts/perf/bench.js --scenario <경로> [--save-baseline] [--compare]
```

| 옵션 | 동작 |
|---|---|
| (없음) | 측정만 |
| `--save-baseline` | 결과를 `.claude/state/perf-baseline.json` 에 기준선으로 저장 |
| `--compare` | 기준선과 비교해 악화·유지·개선 판정 |

**첫 측정이면 `--save-baseline` 을 쓴다.** 기준선이 있으면 `--compare` 를 기본으로 하고, 이번 결과를 새 기준선으로 삼을지는 따로 묻는다.

**종료 코드**

| 코드 | 의미 |
|---|---|
| 0 | 정상. 임계 위반과 악화 없음 |
| 1 | 임계 위반 또는 기준선 대비 악화 |
| 2 | 잘못된 인자 |
| 3 | 서버 응답 없음 |
| 4 | 내부 오류 |

## Phase 4: 결과 제시

```
📈 성능 측정 — list-api

  목록 조회  GET /api/items?page=1
    요청 2273 · 처리량 1127/s · 오류율 0%
    p50 4ms · p95 11ms · p99 18ms · 최대 42ms

  상세 조회  GET /api/items/1
    요청 216 · 처리량 106/s · 오류율 0%
    p50 46ms · p95 48ms · p99 51ms · 최대 63ms

기준선 대비
    목록 조회  11ms → 8ms   (0.73)  개선
    상세 조회  48ms → 48ms  (1.00)  유지

─────────────────────────────
판정: 🟢 임계 위반 없음
─────────────────────────────
```

### 숫자를 읽는 법

**p95 를 본다.** 평균은 느린 요청 몇 개를 가린다. 스무 명 중 한 명이 겪는 시간이 p95 다.

**오류율이 0이 아니면 응답 시간 숫자를 믿지 않는다.** 빨리 실패하는 요청이 평균을 끌어내린다.

**처리량이 낮은데 응답 시간이 짧으면** 동시성 설정이 낮아서일 수 있다. 올려서 다시 잰다.

**기준선 대비 1.2배 이상 느려지면 악화로 판정한다.** 그 아래는 측정 변동일 수 있다.

## Phase 5: 후속

측정 결과에 따라 하나만 제안한다.

| 결과 | 제안 |
|---|---|
| 임계 위반 | 어느 부분이 느린지 확인 필요. `/investigate` 로 원인 추적 |
| 기준선 대비 악화 | 최근 변경 중 무엇이 원인인지 확인. `git log` 로 범위 좁히기 |
| 목표 대비 여유 있음 | 캐시나 복제를 붙이지 않는다. 지금 필요 없다 |
| 첫 측정 | 기준선으로 저장. 다음 측정과 비교할 근거가 생긴다 |
| 구조 변경이 필요해 보임 | `/architecture` 로 재검토. 잰 결과가 근거가 된다 |

```
✅ 측정 완료.

<위 표에 해당하는 제안 한 줄>

- 기준선으로 저장: "저장해줘"
- 결과를 ADR 로 기록: /decision
- 종료: "나중에"
```

**개선을 바로 시작하지 않는다.** 무엇이 느린지 모르는 상태에서 코드를 고치면 추측 최적화가 된다. `/investigate` 로 원인을 좁힌 뒤 `/task` 로 넘어간다.

측정 결과가 아키텍처 결정의 근거가 되면 `/decision` 으로 남긴다. "캐시를 붙이지 않기로 했다, 목표 500ms 에 p95 가 11ms 라서" 같은 것도 기록할 값어치가 있다.

---

## `/ship` 과의 연동

`/ship` 이 성능 회귀를 감지하면 이 커맨드를 안내한다. 기준선이 저장돼 있어야 비교가 가능하므로, 마일스톤이 끝날 때마다 기준선을 갱신해 두는 것이 좋다.

---

## 실패 시나리오

| 상황 | 대응 |
|---|---|
| 서버 응답 없음 | 켜달라고 안내 후 중단 |
| 대상이 운영 환경으로 보임 | 중단하고 확인받는다 |
| 인증 토큰 만료 | 오류율이 100% 로 나온다. 토큰을 새로 받아 재시도 |
| 측정값 변동이 큼 | duration 을 늘리고 다시 잰다. 로컬은 다른 프로그램의 영향을 받는다 |
| 기준선이 없음 | 비교를 건너뛰고 `--save-baseline` 권장 |
| 쓰기 요청으로 데이터가 쌓임 | 정리 방법을 사용자와 정한다 |
