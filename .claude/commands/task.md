# /task — 작업 진입

당신(메인 AI)은 `docs/tasks.md` 의 다음 작업에 진입한다. 작업을 고르고, 관련 문서를 로드하고, 구현 대화로 넘긴다.

**완료 처리는 이 커맨드가 하지 않는다.** 구현이 끝나면 `/done` 이 검증과 체크오프와 커밋을 맡는다.

---

## 이 커맨드만의 규칙

> 말투, 승인 절차 같은 공통 규칙은 `CLAUDE.md` 의 공통 작업 규칙을 따른다.

1. **맥락 로드와 시작 확인까지만 한다.** 구현은 자연 대화로 이어간다.
2. **승인 없이 코드를 쓰지 않는다.**
3. **의존성을 확인한다.** 선행 작업이 미완료면 경고하되 강제로 막지는 않는다.

---

## Phase 0: 선행 체크

1. `docs/tasks.md` 존재 확인. 없으면 `/kickoff` 안내 후 중단.
2. 미완료 항목이 있는지 확인. 없으면 안내 후 종료.

```
현재 마일스톤의 작업이 모두 완료됐습니다.

- 새 기능 시작: /feature-start <기능명>
- 전체 상황 확인: /project-status
- 마일스톤 마무리: /compile-spec
```

3. 브랜치 확인.

```bash
git branch --show-current
```

`main` 이나 `master` 에 있으면 알린다. 기능 작업이면 `/feature-plan` 이 만든 브랜치로 옮겨야 한다.

```
⚠️ 현재 base 브랜치에 있습니다.

이 작업이 어느 기능에 속하는지 확인하고 해당 브랜치로 옮기는 것을 권합니다.
공통 작업이거나 의도한 것이면 그대로 진행해도 됩니다.
```

## Phase 1: 작업 선택

### 1-1. 인자가 있을 때

| 인자 예시 | 매칭 |
|---|---|
| `/task JWT` | 제목에 "JWT" 포함 |
| `/task C1` | `[C1]` 같은 리뷰 발견사항 ID |
| `/task 기능: signup` | signup 기능 아래 다음 미완료 항목 |

후보가 여럿이면 사용자에게 고르게 한다.

### 1-2. 인자가 없을 때

우선순위 순으로 찾는다.

1. 진행 중(`⏳`) 표시된 항목 — 이어받기
2. 현재 마일스톤의 미완료 항목 중 의존성이 해결된 것
3. 여럿이면 상위 세 개를 제시하고 고르게 한다

## Phase 2: 맥락 로드

### 2-1. 기능 식별

`tasks.md` 에서 이 작업이 속한 `### 기능: <X>` 헤더를 찾는다. `### 공통 / 인프라` 아래면 공통으로 분류한다.

### 2-2. 관련 문서 로드

기능이 식별되면 Read 로 로드한다.

| 문서 | 무엇을 얻나 |
|---|---|
| `docs/features/<X>/functional-spec.md` | 이 작업이 구현할 동작 규칙 |
| `docs/features/<X>/tech-spec.md` | 코드 수준 설계. 해당 섹션 |
| `docs/features/<X>/screens.md` | 화면 작업이면 구성과 상태별 표시 |
| `docs/features/<X>/prd.md` | 왜 만드는지. 판단이 필요할 때만 |

공통으로도 로드한다.

| 문서 | 무엇을 얻나 |
|---|---|
| `CLAUDE.md` | 코드 규약, 패키지 구조, 예외 처리 방식, 테스트 규칙 |
| `docs/architecture.md` | 이 작업이 지켜야 할 구조 제약 |
| `docs/data-model.md` | 데이터를 건드리는 작업이면 |
| `docs/context.md` | `[feature: <X>]` 와 `[architecture]` 태그 ADR |

**`CLAUDE.md` 의 프로젝트 고유 규칙을 반드시 확인한다.** 패키지를 어디에 두고 예외를 어떻게 처리하고 테스트를 어디까지 쓰는지가 거기 있다.

### 2-3. 의존성 확인

작업 설명에 "의존: X" 가 있으면 선행 작업의 상태를 확인한다. 미완료면 경고하고 진행 여부를 묻는다.

## Phase 3: 맥락 요약 제시

```markdown
📋 다음 작업

**<작업 제목>** [Effort]
- 소속: 기능: <X> > <카테고리>
- 브랜치: <현재 브랜치>
- 의존: <선행 작업과 상태> (있으면)

**구현할 동작** (functional-spec)
- <해당 기능의 규칙 요약 1~3줄>

**설계** (tech-spec §<섹션>)
- <핵심 설계 요약 1~2줄>

**지켜야 할 것**
- <CLAUDE.md 의 관련 규약 — 예: 기능별 패키지, 업무 예외는 전역 핸들러>
- <architecture.md 의 관련 제약 — 예: DB 접근은 repository 계층에서만>

**관련 결정** (ADR)
- <날짜> [태그] <요약>  (없으면 생략)

시작할까요?
- "시작" → 구현 대화 진입
- "상세" → 설계 문서의 해당 섹션 전문
- "다른 작업" → 다른 후보 제시
- "나중에" → 종료
```

## Phase 4: 구현 진입

### 4-1. 진행 중 표시

`tasks.md` 의 해당 항목 옆에 `⏳` 를 붙인다. 체크박스는 `[ ]` 그대로 둔다.

### 4-2. 구현

동작 규칙과 설계를 기준으로 구현한다. 자연 대화로 진행하며 사용자 승인을 받아 코드를 쓴다.

**구현 중에 다음이 나오면 기억해 둔다.** `/done` 이 후속 조치를 판단할 근거가 된다.

- 아키텍처나 데이터 모델에 영향을 주는 변경
- 라이브러리나 외부 서비스 채택
- 보안에 관련된 처리
- 설계 문서와 실제 구현이 어긋난 지점

**설계와 다르게 구현해야 할 이유가 생기면** 그 자리에서 사용자에게 알린다. 조용히 다르게 만들면 문서와 코드가 벌어진다.

### 4-3. 구현이 끝나면

사용자가 완료를 알리면 `/done` 을 안내한다.

```
구현이 끝났으면 /done 으로 완료 처리하세요.
AC 검증 → 체크오프 → 커밋을 진행합니다.
```

사용자가 "완료" 라고만 말해도 `/done` 흐름으로 넘어간다. `.claude/commands/done.md` 를 Read 로 로드하고 그 지시를 이어서 수행한다.

## 실패 시나리오

| 상황 | 대응 |
|---|---|
| tasks.md 의 작업이 전부 완료 | `/feature-start` 또는 `/compile-spec` 안내 후 종료 |
| 인자 매칭 실패 | 후보 세 개 제시 |
| 의존성 미해결 | 경고 후 진행 여부 확인. 강제로 막지 않는다 |
| functional-spec 이나 tech-spec 없음 | 경고 후 "설계 문서 없이 진행할까요" 확인 |
| base 브랜치에 있음 | 알리고 옮길지 확인. 공통 작업이면 그대로 진행 |
| 구현 중 범위를 벗어난 요청 | 경고 후 PRD 수정이나 새 기능 시작 권장 |
| 설계와 다르게 구현해야 함 | 그 자리에서 알리고 문서를 고칠지 확인 |
