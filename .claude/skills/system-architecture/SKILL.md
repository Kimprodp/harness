# System Architecture — 시스템 구조 설계

## 역할

제품이 어떤 모양의 시스템인지를 정한다. PRD 가 "무엇을 왜 만드는가" 이고 `tech-spec` 이 "이 기능을 어떤 코드로 쓰는가" 라면, 이 스킬은 그 사이를 채운다.

여기서 내리는 결정이 나중에 바꾸기 가장 비싸다. 함수 이름은 언제든 바꾸지만, 데이터를 어디에 어떤 구조로 넣을지는 한번 쌓이기 시작하면 되돌리기 어렵다.

**설계를 물어보는 자리가 아니라 설계를 제안하는 자리다.** 경험 많은 개발자가 옆에 앉아 자료를 읽고 "이 프로젝트는 이게 제일 위험하니 여기부터 확인합시다", "이 규모면 서비스를 쪼갤 이유가 없습니다" 하고 근거를 대며 안을 내놓는 방식으로 진행한다. 사용자는 그 안을 보고 자기가 아는 맥락으로 고친다.

빈칸을 내밀고 채워달라고 하지 않는다. 사용자가 아키텍처를 안다고 가정하지 않는다.

## 핵심 원칙

### 1. 사실은 묻고 판단은 제안한다

**사실**은 사용자만 안다. 데이터가 얼마나 쌓이는지, 사용자가 몇 명인지, 사내 규정이 무엇인지. 이건 묻는다.

**판단**은 사용자가 모른다고 전제한다. 무엇을 검증할지, 어떤 구조로 갈지, 무엇을 지금 정하고 무엇을 미룰지. 이건 **자료를 읽고 안을 먼저 내놓은 뒤 확인받는다.** "패키지 구조를 어떻게 할까요" 라고 되묻지 않는다.

**사실도 되도록 묻지 않는다.** 기획 문서와 기존 코드에 답이 있는 것은 읽어서 채우고 확인만 받는다. 빈칸을 사용자에게 채우게 하면 인터뷰가 길어지고, 사용자는 이미 문서에 쓴 것을 또 말하게 된다.

**사용자가 "모르겠다" 고 하면 그것으로 끝내지 않는다.** 모르니까 이 스킬이 있는 것이다. 추정안을 근거와 함께 제시하고 확인받는다. "정하고 오세요" 로 되돌려 보내지 않는다.

모든 제시는 아래 형식을 따른다. 형식이 고정돼야 매번 같은 품질로 나온다.

```
권장          <안>
근거          Step 1~2 의 어떤 답 때문인지 — 구체적으로 인용
얻는 것       이 선택으로 무엇이 쉬워지는가
잃는 것       무엇이 어려워지거나 늘어나는가
다른 안       대안과, 그것이 나아지는 조건
다시 볼 신호  나중에 이런 게 보이면 재검토한다
```

**"다시 볼 신호" 를 빠뜨리지 않는다.** 이 줄이 있어야 `@architect` 가 나중에 검사할 근거가 생긴다. 추측으로 "지금 바꿔야 하나" 를 묻는 게 아니라 적어둔 신호가 실제로 나타났는지를 본다.

### 2. 묻는 단계와 정하는 단계를 분리한다

Step 1 에서는 아무것도 고르지 않는다. 사실만 모은다. 데이터의 모양을 모르는 채 DB 를 고르면 근거 없는 선택이 된다.

### 3. 되돌리기 어려운 것만 지금 정한다

| 지금 정한다 | 필요해진 다음에 붙인다 |
|---|---|
| 데이터 저장 방식과 스키마 | 캐시 |
| 식별자 체계, 시각 저장 방식 | 읽기 복제본 |
| 서비스를 몇 개로 나눌지 | 파티셔닝 |
| 동기냐 비동기냐 | 서버 대수 |
| 외부에 여는 API 규격과 응답 형식 | 인덱스 추가 |
| 인증과 권한 방식 | 메시지 큐 |
| 시스템 경계와 외부 연동 | 국제화 |

오른쪽을 미리 만들면 지금 당장 운영 부담과 버그가 늘어난다. 왼쪽을 안 정하면 나중에 전체를 건드린다.

### 4. 확장 지점을 열어두되 확장을 구현하지 않는다

오른쪽 항목들이 나중에 쉽게 들어올 **자리**만 만들어 둔다. 만드는 비용은 거의 없고 안 해두면 나중 비용이 크다.

**기술 검증과 가치 검증 PoC 에는 적용하지 않는다.** 곧 버릴 코드에 계층을 나누는 것은 낭비다. 구조 검증 PoC 부터 적용한다.

구조 검증 PoC 에서는 여기에 하나가 더 붙는다. **임시로 때운 것도 같은 계층을 통과하게 만든다.** 데이터를 스크립트로 직접 넣더라도 그 스크립트가 저장 계층을 거치게 하면, 나중에 진짜 API 로 바꿀 때 껍데기만 갈면 된다. 스크립트가 SQL 을 직접 쓰고 있으면 교체할 때 처음부터 다시 짠다.

- DB 접근을 한 계층에 모은다 → 읽기 분리와 캐시가 그 계층 안에서 끝난다
- 외부 시스템 호출을 인터페이스 뒤에 둔다 → 교체와 재시도 추가가 쉽다
- 무거워질 가능성이 있는 처리를 함수로 떼어 둔다 → 큐로 빼기 쉽다
- 설정값을 코드에 박지 않고 환경변수로 뺀다 → 환경 늘리기 쉽다
- 나중에 나눌 기준이 될 컬럼을 미리 갖는다 → 파티셔닝이 가능해진다
- 모듈 경계를 지킨다 → 서비스로 쪼갤 때 선이 이미 그어져 있다

### 5. 재기 전에 최적화하지 않는다

트래픽이 얼마나 나올지, 읽기와 쓰기 비율이 어떨지는 돌려보기 전에 모른다. 추측으로 설계하면 거의 항상 틀리고 그 복잡도를 계속 지고 간다.

대신 **재는 장치를 먼저 넣는다.** 응답 시간과 쿼리 횟수를 로그로 남겨두면 나중에 어디가 느린지 추측하지 않아도 된다.

## Step 0. 현황 진단 — 재실행일 때만

`docs/architecture.md` 가 이미 있으면 설계부터 시작하지 않는다. **`@architect` 에이전트를 먼저 호출**해 지금 상태를 진단한다.

```
Agent(
  subagent_type: "architect",
  description: "현재 아키텍처 진단",
  prompt: `
docs/architecture.md, docs/data-model.md, CLAUDE.md 와 실제 코드를 대조해
아키텍처 진단 리포트를 반환하라. 사용자와 대화하지 말고 리포트만 반환하라.

이번 진단의 맥락: <단계 전환 / 정기 점검 / 특정 문제 확인 중 무엇인지>
목표 단계: <PoC / MVP / 제품화 중 어디로 가려는지>
`
)
```

리포트를 사용자에게 그대로 전달하고, 그 결과를 근거로 어느 Step 을 다시 밟을지 정한다. 전부 다시 하지 않는다. 진단에서 걸린 것만 손댄다.

진단 없이 재설계에 들어가면 무엇이 문제인지 모른 채 구조를 바꾸게 된다.

## Step 1. 요구 수집

**아무것도 고르지 않는다. 사실만 모은다.** 기술 선택은 Step 3 자리다.

### 진행 방식

1. **먼저 읽고 채운다.** 기획 문서, 기존 코드, `plan.md` 에서 답할 수 있는 항목을 채운다
2. **채운 것을 표로 보여주고 확인받는다.** 틀린 것만 고치면 된다
3. **자료로 알 수 없는 것만 묻는다.** 한 번에 나열해서 묻는다
4. **모른다고 하면 추정안을 제시한다.** 왜 그렇게 추정했는지 근거를 대고 확인받는다

항목을 하나씩 순서대로 묻지 않는다. 사용자가 이미 문서에 쓴 것을 또 말하게 된다.

### 1-0. 이 단계로 무엇을 검증하는가 — PoC 일 때만

> **순서 주의.** 번호는 0이지만 **1-1 부터 1-7 까지 자료를 다 읽은 뒤에** 제안한다. 데이터 성격과 화면 유무와 규모를 모르면 무엇이 위험한지 고를 수 없다. 읽어서 채우는 일이 먼저다.

PoC 는 한 종류가 아니다. 무엇을 확인하려는지에 따라 만드는 방식이 정반대로 갈린다.

**이것도 묻지 않고 제안한다.** 무엇을 검증해야 하는지는 판단이지 사실이 아니다. 사용자가 스스로 좁히기 어려운 것이라 여기서 되물으면 대화가 멈춘다.

기획 문서를 읽고 **가장 위험한 것**을 골라 제안한다. 고르는 기준은 이렇다.

| 기준 | 묻는 것 |
|---|---|
| 지금 모르는가 | 이미 아는 것은 검증할 필요가 없다 |
| 틀리면 비싼가 | 되돌리는 데 얼마나 드는가 |
| 다른 것이 여기에 기대는가 | 이게 틀리면 뒤가 전부 흔들리는가 |
| 성패를 가르는가 | 이것만 되면 나머지는 시간 문제인가 |

넷을 다 만족하는 것이 검증 대상이다.

**후보가 여럿이면 하나로 좁히지 말고 순서를 정한다.** 성격이 다른 위험이 둘 이상 나오는 것은 흔하다. "사람들이 쓸까" 와 "이 모델로 표현되나" 는 둘 다 위험한데 하나만 고르면 나머지가 방치된다.

순서를 정하는 기준은 둘이다.

- **앞의 답이 뒤를 무의미하게 만드는 것부터.** 아무도 안 쓸 것이면 모델이 아무리 좋아도 소용없다. 그러니 사용 여부를 먼저 본다
- **싸게 확인되는 것부터.** 며칠이면 답이 나오는 것을 몇 주 걸리는 것보다 먼저 한다

두 기준은 대개 같은 방향을 가리킨다. 가치 검증이 대체로 싸고, 그 답이 아니면 구조 검증이 무의미하다.

**한 회차에서는 하나만 검증한다.** 둘을 동시에 보면 둘 다 어중간해진다. 대신 회차를 나눈다.

```
PoC 1 — 가치    점검자가 종이 대신 쓰는가          2주
  ↓ 쓴다
PoC 2 — 구조    이 모델로 설비 종류를 표현하는가    4주
  ↓ 표현된다
MVP             나머지 기능
```

회차는 `milestones.md` 에 각각 마일스톤으로 올린다. `architecture.md` 의 단계는 셋(PoC / MVP / 제품화)이지만 PoC 안에 마일스톤이 여러 개일 수 있다. 회차마다 `/architecture` 를 다시 돌린다.

제안은 이 형식으로 낸다.

```
검증 대상        <무엇을 확인할 것인가 — 한 문장으로 좁게>
왜 이것인가      <지금 모르고, 틀리면 비싸고, 뒤가 여기에 기대는 이유>
어떻게 확인하나  <구체적 방법. 무엇을 만들고 무엇을 안 만드는가>
맞다는 신호      <무엇이 관찰되면 맞는 것인가>
틀리다는 신호    <무엇이 관찰되면 접어야 하는가>
이번에 안 볼 것  <다른 후보와, 지금 안 보는 이유>
```

**"틀리다는 신호" 를 빠뜨리지 않는다.** 이게 없으면 PoC 가 끝나지 않는다. 계속 고쳐가며 붙들게 된다.

제안을 사용자가 고치면 그대로 받는다. 사용자가 아는 사업 맥락이 있을 수 있다.

| 무엇을 검증하나 | 무엇이 남나 | 코드를 어떻게 만드나 |
|---|---|---|
| **기술이 되는가** — 이 라이브러리로 되나, 성능이 나오나 | 답 하나 (된다 / 안 된다) | 최소. 확인하면 버린다 |
| **사용자가 가치를 느끼는가** — 이걸 쓸까, 돈을 낼까 | 배운 것. `plan.md` 와 PRD 로 간다 | 최대한 싸게. 코드가 없어도 된다 |
| **이 구조가 도메인을 담아내는가** — 이 모델로 표현되나 | 모델과 구조. 제품의 뼈대가 된다 | 검증 대상은 제품 수준, 나머지는 격리된 최소 |

각각 실패하는 방식이 다르다. 기술 검증에 시간을 오래 쓰면 확인만 하면 될 것을 제품처럼 만들고 있는 것이다. 가치 검증을 견고하게 만들면 아무도 안 쓸 것을 정성껏 만든 것이 된다. 셋 중 가장 비싼 실수다. 구조 검증을 대충 만들면 검증 자체가 성립하지 않는다.

#### 기술이 되는가

가장 빨리 만들고 버린다. 확장 지점도 필요 없다. 곧 버릴 코드에 계층을 나누는 것은 낭비다.

Step 2, 4, 5 를 거의 건너뛴다. Step 3 에서 "가장 빨리 확인할 수 있는 방법" 만 고른다.

#### 사용자가 가치를 느끼는가

**검증 대상이 코드가 아니다.** 사용자 반응이다. 그러니 코드를 견고하게 만들 이유가 없고, 빨리 보여주고 반응을 봐야 하니 최대한 싸게 만든다.

**코드를 만드는 것이 답이 아닐 수 있다.** 이것도 묻지 말고 판단해서 제안한다.

| 방법 | 언제 이게 맞나 |
|---|---|
| 화면 목업을 보여주고 반응을 본다 | 무엇을 만들지는 정했고 사람들이 원하는지가 궁금할 때 |
| 앞만 만들고 뒤는 사람이 처리한다 | 흐름이 말이 되는지가 궁금하고, 자동화가 어려울 때 |
| 설명 페이지에 신청 버튼만 단다 | 관심이 있는지 자체가 궁금할 때 |
| 최소 기능을 실제로 만든다 | 써봐야만 알 수 있는 것일 때 |

위에서 하나를 고르고 **왜 그것인지 근거를 대서 제안한다.** 사용자가 "코드로 만들자" 고 해도, 더 싼 방법으로 같은 답이 나온다면 그 사실을 말한다. 판단은 사용자가 한다.

**"그럼 시스템을 설계합시다" 로 바로 가지 않는다.**

정해야 할 것은 구조가 아니라 이것들이다.

- 무엇을 배우려는가
- 무엇이 관찰되면 맞는 것이고 무엇이 관찰되면 틀린 것인가
- 배운 것을 어디에 남기는가 (`plan.md` 의 문제 정의와 지표, 기능 PRD)

`architecture.md` 가 거의 비는 것이 정상이다. 그 사실과 이유를 문서에 적어 둔다.

#### 이 구조가 도메인을 담아내는가

- **검증 대상은 제품 수준으로 만든다.** 데이터 모델을 검증하는 PoC 면 데이터 모델은 MVP 기준으로 정한다. 대충 만들면 검증이 성립하지 않는다
- **나머지는 최소로 만들되 교체 가능하게 격리한다.** 데이터 등록을 스크립트로 때워도 되지만 그 스크립트가 저장 계층을 통과하게 만든다. 나중에 진짜 API 로 바꿀 때 껍데기만 갈면 된다
- **임시로 만든 것을 기록한다.** 무엇이 임시이고 언제 교체하는지 `architecture.md` 에 남긴다. 안 적으면 그대로 운영에 들어간다

#### 검증이 끝나면

**결과를 남기지 않으면 PoC 를 한 의미가 사라진다.** 다음 회차나 MVP 로 넘어가기 전에 세 곳에 남긴다.

| 무엇 | 어디에 |
|---|---|
| 맞았나 틀렸나, 무엇을 관찰했나 | `context.md` 에 ADR. 태그는 `[milestone: <회차>]` 와 내용에 맞는 것 |
| 배운 것이 제품 방향을 바꾸면 | `plan.md` 의 문제 정의와 지표 |
| 완료 판정과 다음 회차 | `milestones.md` |

**틀렸다는 결과도 똑같이 남긴다.** "이 방식으로는 안 된다" 는 것을 알아낸 것도 성과이고, 안 남기면 나중에 같은 것을 또 시도한다.

`/architecture` 를 다시 돌릴 때 `@architect` 가 지난 회차의 결과가 기록됐는지 확인한다.

#### 좁히기

제안이 넓으면 스스로 좁힌 뒤 낸다. **"온톨로지가 맞는지" 는 검증 대상이 아니다.** 무엇을 만들고 무엇을 안 만들지가 안 정해진다.

| 넓은 것 | 좁힌 것 |
|---|---|
| 온톨로지가 맞는지 | 이 모델로 설비 계측 항목을 표현했을 때 원하는 조회가 되는지 |
| 사용자가 쓸지 | 저장한 링크를 일주일 안에 다시 여는지 |
| 성능이 나오는지 | 십만 건에서 목록 조회가 1초 안에 오는지 |

좁히는 방법은 **관찰 가능한 문장으로 바꾸는 것**이다. 눈으로 확인할 수 있으면 충분히 좁혀진 것이다.

자료가 부족해 제안할 근거조차 없으면, 그 사실을 말하고 무엇을 알아야 제안할 수 있는지 구체적으로 묻는다. "정하고 오세요" 로 되돌려 보내지 않는다.

### 1-1. 계정과 권한

> 로그인이 필요한가요? 사용자 종류가 나뉘나요? 나중에 회사나 조직 단위로 데이터가 갈릴 가능성이 있나요?

**왜 먼저 묻나**: 나중에 붙이려면 모든 데이터에 소유자를 추가하고 모든 조회에 필터를 넣어야 한다. 처음에 자리만 잡아두면 거의 공짜다.

**자리를 만드는 것과 인증을 구현하는 것은 다르다.** 둘을 섞으면 PoC 에 과한 요구가 된다.

| | 언제 |
|---|---|
| 데이터에 소유자 자리를 둔다 | 로그인이 나중에라도 생길 것 같으면 **지금**. 거의 공짜다 |
| 인증을 실제로 구현한다 | 여러 사용자가 실제로 쓰기 시작할 때. PoC 에서 사용자가 한 명이면 미뤄도 된다 |

사용자가 한 명뿐인 PoC 라면 소유자 컬럼만 두고 인증은 미루자고 제시한다. 그러면 나중에 인증을 붙일 때 데이터를 건드리지 않아도 된다.

수집할 것: 로그인 유무, 사용자 종류, 조직 단위 분리 가능성, 외부 인증(소셜 로그인, 사내 SSO) 사용 여부, 지금 실제 사용자 수.

### 1-2. 데이터의 성격

> 어떤 데이터를 다루나요? 데이터끼리 관계가 복잡하게 얽혀 있나요, 아니면 독립적인 덩어리인가요? 시간에 따라 계속 쌓이나요? 과거 값을 보존해야 하나요, 최신만 있으면 되나요?

**왜 묻나**: 저장 방식 선택이 여기서 갈린다. 관계가 얽혀 있으면 관계형, 스키마가 자주 바뀌면 문서형, 연결 자체가 의미를 갖는 데이터면 그래프가 후보가 된다.

수집할 것: 주요 데이터 종류, 관계의 복잡도, 시계열 여부, 이력 보존 필요 여부, 예상 증가 속도, 개인정보 포함 여부.

### 1-3. 밖과 주고받는 것

> 데이터가 어디서 들어오나요? 어디로 나가나요? 실시간이어야 하나요, 하루에 한 번 정도로 충분한가요? 우리 API 를 누가 쓰나요 — 우리 화면만인가요, 다른 팀이나 고객사도 쓰나요?

마지막 질문이 API 규격 선택과 버저닝 필요 여부를 가른다.

수집할 것: 데이터 출처, 전달 대상, 실시간 요구 여부, API 소비자, 연동 프로토콜 제약.

### 1-4. 규모

> 사용자가 몇 명 정도인가요? 열 명? 천 명? 십만 명? 데이터는 얼마나 쌓이나요?

**정확할 필요 없다. 자릿수만 알면 된다.** 자릿수가 다르면 설계가 달라진다.

### 1-5. 화면

> 웹 화면이 있나요? 모바일도 있나요? API 만 제공하나요? 다국어가 필요할 가능성이 있나요?

### 1-6. 도는 곳과 데이터의 성격

> 어디서 돌아가나요? 사내 서버인가요, 클라우드인가요? 인터넷에 공개되나요, 사내에서만 접근하나요?
> **실제 회사 데이터가 들어가나요, 아니면 가짜 데이터로만 돌리나요?**

**마지막 질문이 중요하다.** 실제 회사 데이터가 들어가면 외부 무료 호스팅을 쓸 수 없다. 가짜 데이터로만 돌리는 PoC 면 선택지가 훨씬 넓어진다.

### 1-7. 팀과 개발 방식

> 혼자 개발하나요, 나눠서 하나요? 배포를 얼마나 자주 하나요? 규제나 사내 감사 요구가 있나요?

혼자면 서비스를 쪼갤 이유가 크게 줄어든다. 감사 요구가 있으면 변경 이력을 데이터 모델에 넣어야 한다.

### Step 1 산출

수집 결과를 표로 정리해 사용자에게 확인받는다. 틀린 게 있으면 고치고 Step 2 로 간다.

## Step 2. 데이터 모델

**아직 어느 DB 인지는 정하지 않는다.** 데이터가 어떤 모양인지만 그린다.

### 2-1. 엔티티 뽑기

Step 1-2 의 답에서 명사를 뽑아 엔티티 후보를 만든다. 각각에 대해 묻는다.

- 이게 독립적으로 존재하는가, 다른 것에 딸린 것인가
- 무엇으로 하나를 구분하는가
- 어떤 속성을 갖는가
- 만들어진 뒤 바뀌는가, 한번 쓰면 그대로인가

### 2-2. 관계 그리기

엔티티끼리 어떻게 연결되는지 적는다. 하나가 여럿을 갖는지, 여럿이 여럿과 얽히는지, 연결 자체가 속성을 갖는지.

계정이 있는 시스템이면 **각 엔티티의 소유자가 누구인지**를 여기서 정한다. Step 1-1 에서 조직 단위 분리 가능성이 나왔으면 소유자를 사용자가 아니라 조직으로 잡을지 검토한다.

### 2-3. 수명과 이력

- 지울 수 있는가, 지우면 안 되는가
- 과거 값을 남겨야 하는가
- 얼마나 오래 보관하는가

### 2-4. 데이터 구조에 박히는 결정

**나중에 바꾸면 쌓인 데이터를 전부 변환해야 하는 것들이다.** 원칙 1의 제시 형식으로 안을 먼저 내놓는다.

**단계에 맞는 것만 다룬다.** 전부 묻지 않는다.

| 단계 | 지금 정할 것 | 미룰 것 |
|---|---|---|
| PoC — 기술 검증 | 없음 | 전부 |
| PoC — 가치 검증 | 없음 (Step 2 자체를 건너뛴다) | 전부 |
| PoC — 구조 검증, 데이터 모델이 검증 대상이 아닐 때 | 식별자 체계, 시각 저장 방식 | 나머지는 MVP 에서 |
| PoC — 구조 검증, **데이터 모델이 검증 대상일 때** | **MVP 기준으로 전부** | — |
| MVP | 식별자, 시각, 동시 수정 대비, 변경 이력, 개인정보 | 파티션 기준 |
| 제품화 | + 파티션 기준 후보 | — |

**데이터 모델을 검증하려고 만드는 PoC 면 데이터 모델을 대충 만들지 않는다.** 검증 대상을 대충 만들면 검증이 성립하지 않는다.

미루는 항목도 **왜 지금 안 정하는지** 를 한 줄 남긴다. 나중에 그 줄을 보고 판단한다.

**식별자 체계** — 순번으로 할지 UUID 로 할지. 순번을 URL 에 그대로 노출하면 번호만 바꿔 남의 데이터를 조회하려는 시도가 가능해지고, 전체 건수도 드러난다. 외부에 노출하는 식별자를 내부 식별자와 분리할지 정한다.

**시각 저장 방식** — UTC 로 저장하고 보여줄 때 변환할지, 지역 시간으로 저장할지. 안 정하고 섞이기 시작하면 나중에 어느 값이 어느 기준인지 알 수 없다. 기본 권장은 UTC 저장이다.

**동시 수정 대비** — 같은 데이터를 두 요청이 동시에 고치면 하나가 덮인다. 막으려면 버전 컬럼이나 수정 시각 비교가 필요한데, 데이터 모델에 있어야 하는 것이라 나중에 붙이기 어렵다. 동시 수정이 실제로 일어날 수 있는 엔티티를 골라 표시한다.

**변경 이력** — 누가 언제 무엇을 바꿨는지 남길지. 나중에 붙이면 그전 이력이 없다. Step 1-7 에서 감사 요구가 나왔으면 필수다.

**개인정보** — 어떤 필드가 개인정보인지 표시하고, 암호화 대상과 삭제 요청 대응 방식을 정한다.

**나중에 나눈다면 무엇을 기준으로** — 파티셔닝 자체는 나중 일이지만, 나눌 기준이 될 컬럼은 처음부터 있어야 한다. 회사별로 나눌 거면 회사 식별자가, 기간별이면 시각 컬럼이 필요하다. 후보만 적어 둔다.

### 2-5. 산출

`docs/data-model.md` 초안. 엔티티 목록, 속성, 관계, 수명 정책, 2-4 의 결정. 관계는 ASCII 다이어그램이나 표로 그린다.

이 시점에 데이터의 모양이 드러나 있어야 Step 3 의 DB 선택이 근거를 갖는다.

## Step 3. 기술 선택

**Skill 도구로 `tech-stack-decision` 스킬을 로드**하여 수행한다. Step 1 과 2 의 결과를 근거로 사용한다.

정하는 것: 언어와 프레임워크, 데이터 저장소, 초기 배포 방식.

### 배포 방식은 단계에 맞게

PoC 단계에서 클라우드 정식 구성을 갖출 필요가 없다. Step 1-6 에서 실제 회사 데이터가 들어가지 않는다고 확인됐으면 무료 구간이 있는 서비스로 가볍게 띄울 수 있다.

| 대상 | 후보 |
|---|---|
| 프론트 | Vercel, Netlify, Cloudflare Pages |
| 백엔드 | Railway, Render, Fly.io |
| DB | Supabase, Neon, PlanetScale |
| 로컬만 | Docker Compose |

**실제 회사 데이터가 들어가면 위를 쓰지 않는다.** 사내 인프라를 쓰거나 로컬에서만 돌린다. 이 판단을 사용자에게 명시적으로 확인한다.

초기 배포는 나중에 바뀌는 것이 정상이다. 지금은 "가장 빨리 띄울 수 있는 것" 을 고르고, 단계가 올라갈 때 다시 정한다.

## Step 4. 시스템 구조

### 4-1. 시스템 경계

우리가 만드는 시스템을 네모 하나로 그리고, 사용자와 외부 시스템을 주변에 놓고 화살표로 잇는다. 무엇이 우리 소관이고 무엇이 아닌지가 여기서 갈린다.

```
        [사용자]
            │
            ▼
   ┌─────────────────┐        ┌──────────────┐
   │   우리 시스템    │◄──────│  외부 시스템  │
   └─────────────────┘        └──────────────┘
            │
            ▼
      [내보내는 곳]
```

### 4-2. 배포 단위 — 모놀리식과 MSA

**기본 권장은 모듈러 모놀리스다.** 하나로 배포하되 안에서 모듈 경계를 지킨다.

근거는 셋이다. 서비스 경계를 잘못 그으면 되돌리기가 가장 비싼데, 경계를 제대로 그으려면 도메인을 충분히 알아야 하고 시작 시점에는 모른다. MSA 는 운영 비용이 크다 — 배포 대상이 여럿이 되고, 서비스 간 호출 실패에 대응해야 하고, 여러 서비스를 걸친 작업의 일관성을 지켜야 하고, 로그가 흩어져 하나의 요청을 추적하기 어려워진다. 그리고 Step 1-7 에서 혼자 개발한다고 나왔으면 MSA 의 가장 큰 이점인 팀별 독립 배포가 아예 없다.

**쪼갤 근거가 되는 것**: 팀이 나뉘어 배포 주기가 부딪힐 때, 특정 부분만 크게 늘려야 할 때, 기술 스택이 달라야 할 때(예: 추론은 파이썬, 나머지는 자바).

모듈러 모놀리스로 시작하면 나중에 쪼갤 때 선이 이미 그어져 있다. 확장 지점 원칙과 같은 얘기다.

**다시 볼 신호**: 배포 하나에 여러 사람의 변경이 몰려 대기가 생긴다, 특정 모듈만 자원을 크게 먹는다, 한 모듈 때문에 전체를 재시작하게 된다, 모듈 하나에 다른 언어가 필요해진다.

### 4-3. 구성 요소 나누기

네모 안을 연다. 따로 배포되는 단위, 또는 모놀리스 안의 모듈을 그린다.

**처음에는 최소로 나눈다.** 대부분의 PoC 는 애플리케이션 하나와 DB 하나면 충분하다.

각 덩어리에 대해 적는다: 무슨 책임을 지는가, 무엇으로 만드는가, 어디서 도는가, 다른 덩어리와 어떻게 이어지는가.

### 4-4. 통신 방식과 규격

**동기와 비동기.** 바로 호출하고 답을 기다릴지, 큐에 넣고 나중에 처리할지. 비동기는 되돌리기 어렵다. 지금 동기로 충분하면 동기로 두되, 무거워질 처리는 함수로 떼어 둬서 나중에 큐로 빼기 쉽게 만든다.

**외부에 여는 API 규격.** Step 1-3 의 소비자 답이 기준이다.

| 규격 | 언제 |
|---|---|
| REST | 브라우저나 다른 팀이나 고객사가 쓴다. 디버깅이 쉽고 도구가 많다. 기본값 |
| gRPC | 내부 서비스끼리, 성능이 중요하고 스키마를 엄격히 맞춰야 한다 |
| GraphQL | 화면마다 필요한 필드가 크게 다르고 클라이언트가 골라 받아야 한다 |

**소비자가 생기면 못 바꾼다.** 되돌리기 어려운 축이므로 지금 정한다.

**API 버저닝.** 외부에 열면 나중에 바꿀 때 기존 소비자를 어떻게 할지 정해야 한다. 처음부터 경로에 버전을 붙일지, 안 붙이고 시작할지.

**응답 형식.** 성공과 실패의 껍데기를 통일할지, 에러를 어떤 모양으로 내려줄지. 나중에 바꾸면 클라이언트를 전부 고쳐야 한다.

### 4-5. 횡단 관심사

기능마다 따로 정하면 제각각이 되는 것들을 한 번에 정한다.

| 항목 | 정할 것 | 언제 |
|---|---|---|
| 인증과 권한 | 어디서 확인하는가, 권한을 어떻게 표현하는가 | PoC 부터 |
| 트랜잭션 경계 | 어디까지가 하나의 작업 단위인가, 중간 실패 시 어떻게 되는가 | PoC 부터 |
| 로그 | 어떤 형식으로 어디에 남기는가, 레벨 기준은 무엇인가 | PoC 부터 |
| 에러 처리 | 업무 오류와 시스템 오류를 어떻게 가르고 사용자에게 무엇을 보여주는가 | PoC 부터 |
| 설정과 비밀 | 설정값과 비밀번호를 어디에 두는가 | PoC 부터 |
| 측정 | 응답 시간과 쿼리 횟수를 어떻게 재는가 | PoC 부터 |
| 파일 저장 | 이미지나 문서를 DB 에 넣는가 별도 저장소에 두는가 | 파일을 다룰 때 |
| 멱등성 | 같은 요청이 두 번 오면 어떻게 되는가 | 결제·외부 연동·재시도가 있을 때 |
| 외부 실패 대응 | 타임아웃, 재시도 횟수, 계속 실패할 때 | 외부 시스템에 붙을 때 |
| 주기 작업 | 정기적으로 도는 작업이 있는가, 어디서 돌리는가 | 있을 때 |
| 레이트 리밋 | 호출 횟수를 제한하는가 | 외부에 공개할 때 |

**측정을 빠뜨리지 않는다.** 재는 장치가 없으면 나중에 추측으로 최적화하게 된다.

### 4-6. 확장 지점 점검

원칙 4의 목록을 하나씩 확인한다. 지금 만들지는 않지만 자리가 열려 있는지 본다.

| 확장 지점 | 열려 있는가 |
|---|---|
| DB 접근이 한 계층에 모여 있는가 | |
| 외부 호출이 인터페이스 뒤에 있는가 | |
| 무거워질 처리가 떼어져 있는가 | |
| 설정이 환경변수로 빠져 있는가 | |
| 응답 시간을 재고 있는가 | |
| 나중에 나눌 기준 컬럼이 있는가 | |
| 모듈 경계가 지켜지고 있는가 | |

### 4-7. 품질 목표

단계에 맞게 적는다. PoC 면 "정하지 않음" 으로 두어도 된다. 다만 **왜 지금 정하지 않는지**를 한 줄 적는다.

## Step 5. 코드 구조와 규약

덩어리 사이가 아니라 덩어리 **안**을 정한다. 여기서 정한 것은 매일 코드를 쓸 때 따르는 약속이 된다.

원칙 1의 제시 형식으로 안을 먼저 내놓는다.

### 5-1. 애플리케이션 아키텍처

| 패턴 | 무엇인가 | 언제 |
|---|---|---|
| 계층형 | Controller → Service → Repository | 업무 규칙이 단순하고 데이터를 넣고 빼는 게 주된 일 |
| 헥사고날 (포트-어댑터) | 도메인 로직을 가운데 두고 웹·DB·외부 시스템을 인터페이스와 구현으로 분리 | 외부 시스템이 여럿이고 바뀔 가능성이 있다, 도메인 로직을 DB 없이 테스트하고 싶다 |
| 클린 아키텍처 | 헥사고날의 변형. 의존이 안쪽으로만 향함 | 헥사고날과 같은 상황. 용어만 다름 |

헥사고날의 값어치는 **바깥을 갈아끼울 수 있다**는 데 있다. Step 1-3 에서 데이터 출처가 여럿이고 늘어날 거라고 나왔으면 이득이 크다. 반대로 화면 하나에 DB 하나면 인터페이스와 파일만 늘고 얻는 게 없다.

**도메인 주도 설계는 별개 판단이다.** 아키텍처 패턴이 아니라 복잡한 업무 규칙을 코드에 담는 접근법이고, 헥사고날과 자주 같이 쓰여 붙어 다니지만 다른 것이다. 업무 규칙이 코드 여기저기 흩어져 관리가 안 될 때 도입 가치가 생긴다. 단순 조회와 저장이 주인 시스템에 애그리거트와 값 객체를 얹으면 코드만 늘어난다.

**다시 볼 신호**: 같은 업무 규칙이 여러 곳에 복사돼 있다, 외부 시스템을 하나 바꾸는데 손댈 파일이 수십 개다, 테스트를 쓰려면 DB 를 반드시 띄워야 한다.

### 5-2. 패키지 구조

**기능별을 권한다.** 언어와 무관하게 같은 선택이 있다.

```
계층별                        기능별
controller/                  user/
  UserController               UserController
  OrderController              UserService
service/                       UserRepository
  UserService                order/
  OrderService                 OrderController
repository/                    OrderService
  UserRepository               OrderRepository
  OrderRepository
```

계층별은 파일이 적을 때 편하지만 스무 개를 넘어가면 무너진다. 한 폴더에 수십 개가 쌓이고, 기능 하나를 고치려면 폴더 셋을 오간다. 기능별은 기능 하나가 한 폴더에 모여서 고칠 때 그 폴더만 보면 되고, 나중에 서비스를 쪼갤 때 폴더째 떼어낼 수 있다.

모듈러 모놀리스로 간다면 기능별이 사실상 필수다. 계층별로 짜 놓고 나중에 쪼개려면 파일을 하나씩 골라내야 한다.

**모듈 간 호출 규칙도 같이 정한다.** 기능 폴더끼리 서로 마음대로 호출할 수 있는지, 정해진 통로로만 부를 수 있는지. 이걸 안 정하면 모듈 경계가 이름뿐이 된다.

### 5-3. 예외 처리와 응답 형식

정할 것:

- 업무 규칙 위반(중복 이메일 같은 것)과 시스템 오류(DB 연결 끊김 같은 것)를 구분하는가
- 예외를 던지는가, 결과 객체를 반환하는가
- 어디서 잡아 HTTP 응답으로 바꾸는가
- 사용자에게 보여줄 메시지와 내부 로그를 어떻게 가르는가
- 에러 코드 체계를 둘 것인가

**기본 권장**: 업무 예외와 시스템 예외를 나누고, 한 곳(전역 핸들러)에서 HTTP 응답으로 변환하고, 스택 트레이스나 SQL 같은 내부 정보를 사용자에게 노출하지 않는다.

4-4 에서 정한 응답 형식과 짝을 맞춘다. 에러 응답의 모양이 여기서 확정된다.

### 5-4. 테스트 전략

정하지 않고 시작하면 테스트가 제각각 쌓이다 결국 아무도 안 믿는 상태가 된다.

**기본 방향**: 단위 테스트를 많이, 통합 테스트를 적당히, E2E 를 소수로. E2E 는 느리고 자주 깨져서 많아지면 아무도 안 돌린다.

**모킹 원칙**: 내가 소유하지 않은 것만 모킹한다. 외부 API 는 모킹하고, 내 DB 는 실제로 띄워서 테스트한다. 단위 테스트를 과하게 모킹하면 통과해도 실제로 동작하는지 모른다.

정할 것:

| 항목 | 내용 |
|---|---|
| 반드시 테스트하는 것 | 업무 규칙, 경계값, 실패 경로 |
| 테스트하지 않는 것 | 단순 위임, 프레임워크가 보장하는 것 |
| 외부 의존성 | 무엇을 모킹하고 무엇을 실제로 띄우는가 |
| 테스트 파일 위치 | 소스 옆인가 별도 폴더인가, 이름 규칙은 |
| 테스트 데이터 | 어떻게 준비하고 어떻게 정리하는가 |
| CI 에서 돌리는 것 | 어느 종류를 언제 돌리는가 |

**커버리지 숫자 목표는 권하지 않는다.** 숫자를 채우려고 의미 없는 테스트가 늘어난다. "새 업무 규칙에는 테스트를 붙인다" 같은 규칙이 실제로 작동한다.

기능 하나의 테스트 계획은 `tech-spec` 스킬이 커버리지 다이어그램까지 깊게 다룬다. 여기서 정하는 건 그 위층의 전체 전략이다.

### 5-5. 코딩 규약과 자동화

**사람이 지키는 규칙보다 도구가 강제하는 규칙을 쓴다.** 포맷터와 린터를 붙이고 저장할 때 자동으로 돌게 하면 규약 문서를 안 읽어도 지켜진다. `.claude/hooks/post-edit.example.js` 를 복사해 연결하면 된다.

도구로 못 잡는 것만 문서로 남긴다. 이름 짓는 기준, 커밋 메시지 형식, 의존성을 새로 추가할 때의 기준, 환경변수 이름 규칙, 주석을 쓰는 기준.

## 단계별로 어디까지

| 단계 | Step 1 | Step 2 | Step 3 | Step 4 | Step 5 |
|---|---|---|---|---|---|
| PoC — 기술 검증 | 1-0, 1-2, 1-6 만 | 엔티티와 관계만 | 가장 빨리 확인할 방법 | 생략 | 생략 |
| PoC — 가치 검증 | 1-0, 1-5, 1-6 만 | 생략 | 가장 싸게 보여줄 방법 | 생략 | 생략 |
| PoC — 구조 검증 | 전부 (얕게) | 엔티티·관계·식별자·시각 | 언어·DB·가벼운 배포 | 경계, 덩어리, 동기/비동기, 기본 횡단 관심사, 확장 지점 | 아키텍처 패턴, 패키지 구조, 예외 처리, 최소 테스트 |
| MVP | 다시 확인 | 스키마 확정, 동시 수정, 변경 이력 | 배포 재검토 | API 규격·버저닝·응답 형식, 환경 분리, 인증, 로그 | 테스트 전략 확정, 린터 자동화 |
| 제품화 | 다시 확인 | 마이그레이션 정책, 파티션 기준 | 인프라 재검토 | 잰 결과 기반 보강, 멱등성, 레이트 리밋, 모니터링 | 규약 정비, CI 테스트 확장 |

**이 표는 기본선이고, 검증 대상은 여기서 예외다.** 구조 검증 PoC 에서 검증 대상에 해당하는 영역은 한 단계 위(MVP) 기준으로 올려 정한다. 데이터 모델을 검증하면 Step 2 를 MVP 기준으로, 통신 구조를 검증하면 Step 4 를 MVP 기준으로.

PoC 인터뷰가 길어지지 않게 한다. 해당 열에 없는 항목은 묻지 않고 "다음 단계에서 정함" 으로 적는다.

## 단계가 올라갈 때

Step 0 진단을 먼저 돌린 뒤, 아래 목록을 펼쳐 **무엇이 필요한지 후보를 먼저 내놓는다.**

### PoC 에서 MVP 로

- **`architecture.md` 의 "임시로 만든 것" 을 하나씩 처리** — 교체했거나, 남겨도 되는 이유가 있거나 둘 중 하나여야 한다
- 임시 저장소를 실제 DB 로 교체
- 인증과 권한 붙이기
- 개발 환경과 운영 환경 분리
- 에러 처리 정비 (삼키지 않기, 사용자 노출용과 내부용 구분)
- 로그와 응답 시간 기록
- 백업 방식 정하기
- 스키마 변경 절차 세우기
- API 규격과 버저닝 확정
- 테스트 전략 확정

### MVP 에서 제품화로

- 실제 부하 측정 (`/perf`)
- 잰 결과를 근거로 필요한 곳에만 캐시나 읽기 분리
- 멱등성과 레이트 리밋
- 모니터링과 알림
- 배포 자동화
- 장애 대응 절차
- 보안 전면 감사 (`/security-audit`)

필요 없다고 판단한 것도 **왜 필요 없는지** 를 한 줄로 남긴다.

**"임시로 만든 것" 을 빠뜨리지 않는다.** 구조 검증 PoC 에서 등록 스크립트나 하드코딩한 설정처럼 나중에 걷어낼 것을 적어 둔다. 적지 않으면 그대로 남아 운영에 들어간다. `@architect` 가 단계 전환 때 이 목록이 정리됐는지 검사한다.

### `docs/data-model.md`

```markdown
# 데이터 모델

## 엔티티
<목록과 각각의 식별자·속성·소유자>

## 관계
<다이어그램 또는 표>

## 구조 결정
<식별자 체계, 시각 저장 방식, 동시 수정 대비, 변경 이력, 개인정보, 파티션 기준 후보>

## 수명과 이력
<보존 기간, 삭제 정책, 이력 보관 여부>

## 저장 위치
<어떤 엔티티가 어디에 어떤 형태로>

## 스키마 변경 절차
<마이그레이션을 어떻게 적용하고 되돌리는가>
```

### `CLAUDE.md` 프로젝트 고유 규칙

매일 코드를 쓸 때 따르는 약속은 여기 둔다. 세션마다 자동으로 읽히는 파일이라 실제로 지켜진다.

- 패키지 구조와 모듈 간 호출 규칙
- 예외 처리 방식과 응답 형식
- 테스트를 어디까지 쓰는가
- 코딩 규약 중 도구로 못 잡는 것

### ADR

각 Step 에서 내린 결정은 `docs/context.md` 에 ADR 로 남긴다. 태그는 `[architecture]`, `[data]`, `[tech]`, `[infra]` 를 상황에 맞게 쓰고, 단계 전환 중이면 `[milestone: <이름>]` 을 함께 붙인다.

## 안티패턴

❌ 데이터 성격을 모른 채 DB 를 고른다
❌ 트래픽을 재기 전에 캐시와 읽기 복제본을 설계한다
❌ 사용자가 말하지 않았다는 이유로 계정과 권한을 건너뛴다
❌ PoC 인데 서비스를 다섯 개로 쪼갠다
❌ "패키지 구조 어떻게 할까요" 라고 사용자에게 되묻는다
❌ "무엇을 검증하려 하시나요" 라고 묻고 답을 기다린다 — 자료를 읽고 제안한다
❌ 사용자가 "모르겠다" 고 하자 "정하고 오세요" 로 되돌려 보낸다
❌ 기획 문서에 이미 적힌 것을 다시 묻는다
❌ 검증 대상을 "온톨로지가 맞는지" 처럼 넓게 둔 채 설계에 들어간다
❌ 안을 제시하면서 얻는 것만 말하고 잃는 것을 안 말한다
❌ "다시 볼 신호" 를 안 적어서 언제 재검토할지 아무도 모른다
❌ 아키텍처 문서에 v1, v2 를 남겨 이력을 쌓는다
❌ 재실행인데 진단 없이 바로 재설계에 들어간다

✅ 묻고, 그리고, 그다음에 고른다
✅ 안을 먼저 내고 트레이드오프를 함께 말한다
✅ 지금 안 정하는 것은 **왜 안 정하는지** 를 적는다
✅ 확장 지점만 열어두고 확장은 필요할 때 만든다
